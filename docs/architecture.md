# Архитектура tia-text-sync

## Верхнеуровневая схема

```text
┌──────────────────────────────────────────────────────────────────────┐
│                         WinForms GUI (MainForm)                       │
│  [TIA Portal ▼] [Рабочая папка] [Экспорт] [Импорт*] [Инструменты ▼] │
│                         Строка состояния / путь к папке               │
└───────┬────────────────────────────────────────────┬─────────────────┘
        │ await _sta.RunAsync(...)                   │ Progress<string>
        ▼                                            ▼ (UI SyncContext)
┌───────────────┐      ┌──────────────────────────────────────────────┐
│  StaWorker    │      │               UI-поток                        │
│  (TIA-STA)    │      │  TreeView  ·  TextBox (лог)  ·  StatusStrip   │
│               │      └──────────────────────────────────────────────┘
│  TiaSession   │
│  ProjectSvc   │──▶ ExportService ──▶ blocks/ tags/ types/
│  TreeBuilder  │──▶ HwExportService ▶ hw.xml
└───────────────┘
        │
        ▼
┌───────────────────┐
│  TIA Portal        │
│  (Openness COM)    │
└───────────────────┘

* Импорт — в разработке
```

## Потоковая модель

Openness API — COM out-of-process сервер. TIA Portal доставляет колбэки как Win32-сообщения в STA-поток вызывающей стороны. Если этот поток заблокирован внутри `WndProc` (как происходит с `Control.BeginInvoke` и `WindowsFormsSynchronizationContext.Post`), COM не может диспетчеризировать колбэки → **дедлок**.

**Решение — `StaWorker`**: выделенный STA-поток с «сырым» циклом Win32 (`GetMessage`). Работа отправляется через `PostThreadMessage` (hwnd=NULL) — такие сообщения обрабатываются **прямо в теле цикла**, не внутри `WndProc`. COM может свободно прокачивать очередь во время любого блокирующего вызова TIA.

```text
UI-поток               StaWorker (TIA-STA)
─────────              ───────────────────
await RunAsync(work)   GetMessage → work()   ← TIA вызовы здесь
UI ждёт Task           COM колбэки доставляются свободно
Task завершён ────────▶ продолжение на UI-потоке
```

## Структура пакетов

```text
TiaTextSync/
  Core/
    StaWorker.cs         — выделенный STA-поток, PostThreadMessage-цикл
    TiaSession.cs        — подключение к TIA Portal / запуск нового процесса
    WorkspaceService.cs  — рабочая папка (Git-репозиторий), персистентность
    Logger.cs            — потокобезопасный файловый лог с временными метками
    OpennessResolver.cs  — загрузка сборок Openness из установки TIA Portal V21

  Services/
    ProjectService.cs    — открытие проекта, перечисление устройств и ПЛК
    ExportService.cs     — экспорт блоков (SCL/AWL/DB/XML), тегов (XML), UDT
    HwExportService.cs   — снимок HW-конфигурации в XML (diff only)
    XmlNormalizer.cs     — удаление нестабильных полей из XML
    BlockTextRenderer.cs — текстовый вид блоков LAD/FBD для чтения и diff
    PlcCompiler.cs       — компиляция программы ПЛК перед экспортом (по кнопке-флажку)
    PlcCatalog.cs        — список элементов ПЛК с папками групп, общий для дерева, экспорта и сравнения
    CompareService.cs    — сравнение с рабочей папкой через экспорт во временную папку
    PathNames.cs         — имена папок устройств и ПЛК в рабочей папке

  UI/
    MainForm.cs          — главное окно WinForms
    TreeBuilder.cs       — построение TreeNode из COM-объектов TIA

  Program.cs             — точка входа, инициализация Logger, Application.Run
```

## Компоненты

### StaWorker

Выделенный STA-поток с «сырым» Win32-циклом сообщений (`GetMessage/PostThreadMessage`). Все обращения к TIA Portal Openness API выполняются через `RunAsync(work)`. Позволяет избежать дедлока COM ↔ WndProc.

### TiaSession

Управляет жизненным циклом TIA Portal:

- **Подключение к работающему TIA Portal** — через `TiaPortal.GetProcesses()`, не трогает проекты
- **Запуск нового экземпляра** — если TIA Portal не запущен; закрывает его при `Dispose()`

Создаётся и используется исключительно на потоке `StaWorker`.

### WorkspaceService

Хранит путь к корневой папке Git-репозитория. Путь сохраняется в `%AppData%\TiaTextSync\workspace.txt` между запусками.

### ProjectService

Открывает TIA-проект, перечисляет устройства и ПЛК:

- `GetOpenProject()` — возвращает первый уже открытый проект
- `OpenProject()` — открывает файл или переиспользует уже открытый (по пути)
- `GetAllPlc(project)` — `Device → DeviceItem → SoftwareContainer → PlcSoftware`
- `GetDeviceGroups(project)` — группировка ПЛК по устройствам для экспорта

### ExportService

Экспортирует содержимое одного `PlcSoftware` в три подпапки:

| Метод | Источник | Папка | Расширение | Round-trip |
| ----- | -------- | ----- | ---------- | ---------- |
| `ExportBlockAsSource` | `IGenerateSource.GenerateSource()` | `blocks/<группы>/` | `.scl` / `.awl` / `.db` | ✅ |
| `ExportBlockAsXml` | `PlcBlock.Export()` | `blocks/<группы>/` | `.xml` | ✅ `PlcBlockComposition.Import` |
| `ExportTagTable` | `PlcTagTable.Export()` | `tags/<группы>/` | `.xml` | ✅ `PlcTagTableComposition.Import` |
| `ExportType` | `IGenerateSource.GenerateSource()` | `types/<группы>/` | `.scl` | ✅ |
| `ExportTechnologicalObject` | `TechnologicalInstanceDB.Export()` | `tech/<группы>/` | `.xml` | ✅ `TechnologicalInstanceDBComposition.Import` |

Примечания:

- Папки повторяют группы проекта TIA Portal. Символы, недопустимые в именах Windows, из имён удаляются.
- Рядом с XML блока LAD/FBD создаётся текстовый вид `.lad` / `.fbd`: интерфейс и логика каждой сети в виде выражений. Он нужен только для чтения и diff, импорт его не использует.
- Технологические объекты, для которых TIA Portal не поддерживает SimaticML (например, `PID_Compact` на S7-1200), выгружаются как исходник экземплярного DB `.db`. Список `Parameters` для них оказался пустым.
- Системные блоки («Program resources» и др.) экспортируются в `blocks/System blocks/<группа>/`. Их обход идёт отдельно, через `PlcBlockSystemGroup.SystemBlockGroups`. При импорте эти блоки планируется пропускать.
- Формат блока определяется по `ProgrammingLanguage`: `SCL`, `STL` и `DB` экспортируются исходником, все остальные языки (LAD, FBD, GRAPH, F-блоки) в XML. Проверка `is IGenerateSource` не подходит, потому что этот интерфейс реализован самим `PlcBlock`.
- STL-блоки экспортируются с расширением `.awl`, а DB с расширением `.db`: для них TIA Portal отклоняет `.scl`.
- Несогласованные (не скомпилированные) блоки TIA Portal не экспортирует. Проект нужно скомпилировать заранее или включить «Инструменты → Компилировать перед экспортом и сравнением», этот флажок изменяет состояние проекта в TIA.
- Защищённые блоки SCL/STL/DB пропускаются строкой `SKIP` и не считаются ошибкой: TIA Portal не выдаёт их исходник.
- Файлы создаются во временной папке и заменяют файлы в рабочей папке только после успешного экспорта.
- После экспорта из `blocks/`, `tags/`, `types/`, `tech/` и папок прежней раскладки `src/`, `xml/` удаляются файлы `.scl`, `.awl`, `.db`, `.xml`, `.lad`, `.fbd`, `.csv`, которых нет в ПЛК, а также опустевшие папки. Файлы элементов, экспорт которых завершился ошибкой или которые не вошли в выборку, сохраняются.
- Экспортировать можно выбранную ветвь дерева (устройство, ПЛК, группу, элемент), отличия по последнему сравнению или устройство целиком. HW-снимок обновляется при экспорте устройства и при экспорте отличий, если он отличался.

### CompareService

Сравнение запускается вручную: для выбранной ветви дерева или для всего проекта. Элементы экспортируются тем же `ExportService` во временную папку, затем их файлы сравниваются с рабочей папкой без учёта символов CR, которые Git может менять при checkout. Результат однозначен и не зависит от дат изменения в TIA Portal.

Статусы элемента: совпадает, отличается, нет в папке, не скомпилирован, ошибка экспорта. Несогласованные блоки и UDT TIA Portal не экспортирует, поэтому их содержимое недоступно до компиляции: такой элемент почти всегда изменён после последней компиляции, но с рабочей папкой его сравнить нельзя. Признак `IsConsistent` проверяется до экспорта, чтобы дать понятное сообщение вместо исключения Openness. Для ПЛК дополнительно считаются элементы, файлы которых есть в рабочей папке, но которых нет в TIA (удалены в TIA или добавлены через Git). HW-снимок сравнивается с `hw.xml`.

Результаты хранятся в памяти до отключения, смены проекта или рабочей папки. После правок в TIA они устаревают, пока сравнение не запущено снова. Экспорт обновляет статусы выгруженных элементов без повторного сравнения.

### HwExportService

Строит XML-снимок аппаратной конфигурации устройства из свойств Openness API (`Name`, `TypeIdentifier`, `PositionNumber`, `IsPlugged`). Используется только для Git diff — автоматический импорт не поддерживается.

Вывод: `<deviceDir>/hw.xml`

### TreeBuilder

Строит дерево `TreeNode` из COM-объектов TIA, выполняется целиком на потоке `StaWorker`. `TreeNode` — объект данных (не UI-контрол), создавать вне UI-потока безопасно.

Дерево строится из того же списка `PlcCatalog`, что и экспорт, поэтому группы совпадают с папками. Результаты последнего сравнения отмечаются цветом: отличающиеся элементы синим, отсутствующие в папке зелёным, ошибки красным. У групп и ПЛК показывается число отличий и элементов, которых нет в TIA. Дерево перестраивается после сравнения и экспорта, раскрытые узлы, выбор и прокрутка при этом сохраняются.

### XmlNormalizer

Удаляет нестабильные поля из XML-экспорта: `Created`, `InstalledProducts`, `ModifiedDate`, `CreationDate`, `CompileDate`, `CodeModifiedDate`, `InterfaceModifiedDate`, `ParameterModified`, `StructureModified`. Делает `git diff` стабильным при повторном экспорте.

## Структура файлов в репозитории

```text
<workspace>/                    ← корень Git-репозитория
  <SafeDeviceName>/             ← имя устройства (символы "/" заменены)
    hw.xml                      ← снимок HW-конфигурации (diff only)
    <PlcName>/
      blocks/<группы проекта>/
        <BlockName>.scl         ← SCL-блоки
        <BlockName>.db          ← DB
        <BlockName>.awl         ← STL-блоки
        <BlockName>.xml         ← LAD/FBD/GRAPH и F-блоки
        <BlockName>.lad         ← текстовый вид LAD (.fbd для FBD), только для чтения
      tags/<группы проекта>/
        <TableName>.xml         ← таблицы тегов (SimaticML)
      types/<группы проекта>/
        <TypeName>.scl          ← UDT
      tech/<группы проекта>/
        <ObjectName>.xml        ← технологические объекты (SimaticML)
```

## Технологический стек

| Компонент | Выбор | Причина |
| --------- | ----- | ------- |
| Runtime | .NET Framework 4.8 | Требование Openness API |
| Язык | C# (LangVersion latest) | Современный синтаксис: record, pattern matching, using var |
| UI | WinForms | Встроен в .NET 4.8, минимальные зависимости |
| API | Siemens TIA Openness V21 | Единственный официальный способ программного доступа |
| DLL | `Siemens.Engineering.Base` и `Step7` из `PublicAPI\V21\net48` | В V21 API разбит на отдельные сборки. Для компиляции берутся из `libs/V21`, при запуске загружаются из установки TIA Portal |
| SCL | `.scl` / `.awl` | Расширения, генерируемые самим TIA Portal через `GenerateSource` |

## Ключевые ограничения платформы

- Openness API требует x64 и работает только на Windows
- Пользователь должен состоять в группе `Siemens TIA Openness`
- Нельзя открыть проект, уже открытый в GUI — нужно подключаться к существующему процессу
- Экспорт блоков — синхронная операция; для больших проектов занимает несколько минут
