# ADR 004: Стратегия импорта и границы round-trip

**Статус:** Принято
**Дата:** 2026-03-09

> **Обновление 2026-11-11:** импорт реализован в GUI, а не через CLI, описанный ниже. Кнопка «Импорт» загружает выбранную ветвь дерева, отличия по последнему сравнению или устройство целиком, после загрузки элементы сравниваются с рабочей папкой. Устройства лежат в `<Устройство>/`, HW-снимок в `<Устройство>/hw.xml`, а не в `hw/`. Подробности в `docs/architecture.md`, раздел ImportService.

## Контекст

Элементы TIA-проекта делятся на две категории с точки зрения Openness API:

- **Изменяемые программно** — блоки (SCL/LAD/FBD), DB, UDT, Tag Tables
- **Только для чтения / сложно изменяемые** — HW-конфигурация (устройства, модули, Profinet, IP-адреса)

Создание HW-конфигурации через Openness требует работы с Hardware Catalog и является хрупким: зависит от версий GSD-файлов, артикулов модулей и сложной иерархии объектов. Это вне разумного scope прототипа.

## Решение

**Основной сценарий: обновление существующего проекта.**

Репозиторий хранит:

1. Все элементы проекта в текстовых/XML файлах — для полного отслеживания изменений в Git
2. **Базовый шаблон проекта** (`template.ap17`) — с настроенной HW-конфигурацией

Round-trip делится на два класса элементов:

| Класс | Элементы | Экспорт | Импорт |
| ----- | -------- | ------- | ------ |
| **Код** | FB, FC, OB (SCL, STL), DB, UDT | `blocks/**/*.scl`, `*.awl`, `*.db`, `types/**/*.udt` | `GenerateBlocksFromSource` ✅ |
| **Структура** | LAD/FBD блоки, Tag Tables | `blocks/**/*.xml`, `tags/**/*.xml` | `PlcBlockComposition.Import`, `PlcTagTableComposition.Import` ✅ |
| **Конфигурация** | HW Config, Profinet, IP, сеть | `hw/*.xml` | только вручную через TIA GUI ⚠️ |

## Workflow

### Экспорт (sync → files)

```text
tia-text-sync --project MyPLC.ap17 --output ./repo
```

Экспортирует всё: код, теги, HW-конфиг. Всё попадает в Git.

### Импорт (files → sync) — планируется

```text
tia-text-sync --project MyPLC.ap17 --input ./repo
```

Импортирует только `blocks/`, `tags/`, `types/`, подпапки задают группу элемента в проекте. Папка `blocks/System blocks/` пропускается: её блоки создаёт сам TIA Portal. Папка `hw/` **игнорируется** при импорте — изменения в ней требуют ручного вмешательства.

### Структура репозитория

```text
repo/
  template.ap17          # Базовый проект с HW-конфигом (бинарный, в Git LFS или отдельно)
  hw/                    # HW-конфигурация — только для отслеживания изменений в Git
    CPU_1516.xml
    ET200SP_left.xml
  <PlcName>/             # По одному каталогу на каждый ПЛК в проекте
    blocks/              # Блоки, подпапки повторяют группы проекта — полный round-trip
    tags/                # Tag Tables SimaticML XML, с группами — полный round-trip
    types/               # UDT, с группами — полный round-trip
```

## Обоснование

- Хранение `hw/` в XML позволяет видеть в Git: изменили ли IP-адрес, добавили ли модуль — без возможности автоматического применения
- `hw/` находится на уровне outputDir (не внутри PlcName), поскольку устройства существуют на уровне проекта; не все устройства содержат PLC software
- `template.ap17` решает проблему «с чего начать»: разработчик открывает шаблон и запускает импорт
- Компромисс явный и документированный: не «HW не поддерживается», а «HW отслеживается, но применяется вручную»
- Для большинства проектов HW-конфиг меняется редко; код и теги — регулярно

## Последствия

- При изменении `hw/` Git покажет diff, но разработчик обязан применить изменения руками
- `template.ap17` нужно обновлять при изменении HW-конфига (редко)
- Команде нужно договориться о процессе: изменение железа = PR в `hw/` + ручное применение + обновление шаблона
