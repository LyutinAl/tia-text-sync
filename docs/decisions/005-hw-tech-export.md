# ADR 005: Экспорт HW-конфигурации и технологических объектов

**Статус:** Принято
**Дата:** 2026-03-09

## Контекст

После реализации экспорта PLC-логики (блоки, теги, UDT) возникают два следующих по важности слоя:

1. **HW-конфигурация** — физическая структура оборудования (CPU, шасси, IO-модули, PROFINET-сеть, IP-адреса, параметры сети). Хранится в TIA Portal как настройки `Device` / `DeviceItem`.
2. **Технологические объекты (TO)** — Motion Control Axis, PID Controller, Cam, External Encoder и другие объекты из библиотеки TIA.

### HW-конфигурация

TIA Portal Openness API V17 **не предоставляет** `Device.Export()`. Рефлексия DLL подтверждает: ни `Device`, ни `DeviceUserGroup` не имеют методов Export/Import. `Project.ExportProjectTexts()` — только для переводимых текстов.

Доступные через API свойства для построения структурного дампа:

| Объект | Свойства |
| ------ | -------- |
| `Device` | `Name`, `TypeIdentifier`, `IsGsd`, `DeviceItems` |
| `DeviceItem` | `Name`, `TypeIdentifier`, `PositionNumber`, `IsPlugged`, `DeviceItems` |

Этих данных достаточно для отслеживания в Git: добавили ли модуль, изменился ли артикул CPU, сменился ли slot.

### Технологические объекты

В TIA Portal V17 технологические объекты представлены двойственно:

- **В дереве блоков** — каждый TO имеет соответствующий `TechnologicalInstanceDB` в `PlcSoftware.BlockGroup`. Этот Instance DB содержит всю конфигурацию TO (параметры оси, пределы, PID-коэффициенты и т.д.)
- **В HW-конфигурации** — связь TO с физическим приводом/энкодером хранится как часть Device

**Вывод:** конфигурация технологических объектов **уже покрывается** существующим экспортом блоков:

- `TechnologicalInstanceDB` экспортируется в `src/<Name>.scl` (если поддерживает `IGenerateSource`) или `xml/<Name>.xml`
- Привязка к железу отслеживается через `hw/*.xml`

В будущем можно добавить папку `tech/`, куда TO-блоки выносились бы отдельно на основе типа (`block is TechnologicalInstanceDB`). Это потребует изменения только маршрутизации в `ExportService`, не самого механизма экспорта.

## Решение

### HW-конфигурация

Реализовать `HwExportService`:

- Входные данные: `Project` (уровень проекта, не PLC)
- Перебирает `Project.Devices`
- Каждое устройство → `<outputDir>/hw/<DeviceName>.xml` — собственный XML-дамп из доступных API-свойств
- Рекурсивный обход `DeviceItem.DeviceItems` — все вложенные модули
- `Device.Export()` не используется (недоступен в V17 API)

Расположение `hw/` — на уровне `outputDir`, не внутри `<PlcName>/`:

```text
outputDir/
  hw/              ← уровень проекта (device ≠ PLC software)
    CPU_1516.xml
    ET200SP.xml
  PLC_1/           ← уровень PLC software
    src/
    ...
```

### Технологические объекты

Дополнительная реализация не требуется для прототипа. TO уже экспортируются как Instance DB.

Идентификация TO в будущем: проверить `block.GetType().Name` или наличие специфичных атрибутов у блока. Если потребуется — переместить в `tech/` и обновить `ExportService`.

## Обоснование

- Экспорт `hw/` в Git даёт полный аудит изменений оборудования без сложности автоматического импорта
- TO через Instance DB — это не упрощение, а архитектурное решение самого TIA Portal: конфигурация объекта хранится в DB, что и позволяет работать с ней через стандартный API блоков
- Разделение `hw/` и `<PlcName>/` на верхнем уровне отражает реальную иерархию: в одном проекте может быть несколько CPU, HMI-панелей и других устройств

## Последствия

- `HwExportService` принимает `Project`, а не `PlcSoftware` — вызывается один раз на весь проект, не на каждый ПЛК
- `Program.cs` вызывает `HwExportService` после цикла по ПЛК
- При повторном экспорте устройства с тем же именем файл перезаписывается (идемпотентно)
- XML, созданный `HwExportService`, является кастомным форматом — не Simatic ML, не GSD; предназначен только для Git-diff

## Нереализованное (future scope)

- Папка `tech/` для изоляции TO Instance DB от обычных DB
- Импорт HW-конфига через Openness (слишком хрупко для прототипа)
- Поддержка HMI WinCC устройств через отдельный сервис (`Siemens.Engineering.Hmi`)
